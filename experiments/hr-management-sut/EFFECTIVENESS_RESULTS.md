# HR histories: fault detection and representative sensitivity

Recorded 31 October 2026. This experiment follows [SCALE_RESULTS.md](SCALE_RESULTS.md). It keeps the original
scaling benchmark and nine HR intentions intact and adds a separate protocol with
record reads, manager decisions, repeated HR corrections, totals and an independent
second employee. The specification uses the unchanged generic APN and `reviews`
equations. All input/output pairs remain synchronous.

## Frozen experiment

Lengths one through three yield 5, 25 and 125 regions. Each has the engine-selected
representative, a 60-minute representative, and a 720-minute representative:
**155 regions and 465 concrete tests**. The selected duration is 623 minutes at
length one and 15 minutes at lengths two/three. These are the solver's recorded
choices, not choices adjusted after observing mutants. Extra members pass an
independent region/witness check and concrete APN replay.

Each sequence records a 45-minute standard entry for employee 1002, then exercises
employee 1001. It checks all stored work entries, pending versus approved totals,
manager approval/decline, two corrections of the last entry, the other employee's
unchanged record and total, and audit counts. Training is declined; other
non-standard kinds are approved. Full protocols are generated by
[effectiveness-fixture.mjs](experiments/effectiveness-fixture.mjs).

REST runs every test on every variant. Playwright uses six tests fixed before
results: kind vectors [1], [1,3], [1,3,0], each with selected and upper-boundary
representatives. This is a transport cross-check, not full browser coverage.
Expected outputs come from the protocol and APN, never the SUT. Every run resets
November data while preserving 256 seeded staff, 7,680 historical work records and
512 historical vacation records.

## Baseline findings

The first unmutated campaign passed all 465 REST and six browser tests. A repeat
on another database produced two output mismatches followed by 18 database errors.
SQLite `quick_check` reported freelist corruption and an incorrect audit-index
entry count. This failed run is preserved in the compact
[preflight findings](results/effectiveness-preflight-findings.json); it is not
counted as mutation evidence or quietly treated as a passing baseline.

The exact cause of the intermittent corruption remains unresolved. An identical
input rerun passed. The harness now keeps live databases and event logs in an OS
temporary directory, publishes reports atomically after completion, and requires
an explicit database-integrity check. These are containment and evidence-quality
changes, not proof of a database root-cause fix. The backend's unmutated business
rules were not altered.

Two consecutive fresh campaigns pass **465/465 REST tests and 6/6 browser tests**
with intact databases. All final baseline and mutant databases pass the same
integrity check. No errors or inconclusive outcomes occur in the final matrix.
The [baseline repeats](results/effectiveness-baseline-repeats.json) retain both
successful checks; this is evidence of successful repeats, not proof that the
earlier intermittent problem cannot recur.

## Fault detection

Five deliberate new faults supplement the existing pending-total fault. They
exercise a third-entry overwrite, double-counted approval, old contributions left
in totals after correction, another employee changed by correction, and storing
the valid upper duration 720 as 719. The selected mutant set is purposeful, so its
mutation score must not be read as an unbiased estimate for arbitrary software.

| overwrite-earlier | 0/5 | 0/25 | 125/125 | 0/5 / 0/25 / 125/125 |
| approval-double-count | 3/5 | 21/25 | 117/125 | 3/5 / 21/25 / 117/125 |
| correction-adds-old | 5/5 | 25/25 | 125/125 | 5/5 / 25/25 / 125/125 |

Entries are mismatching tests / executed tests. The 60-minute policy has the
same detection counts as the selected policy in this experiment.

The final matrix contains **3,255 REST executions and 42 browser executions**.
All 42 matched API/browser event sequences and verdicts agree. The third-entry
fault survives every shorter history, then fails all length-three tests.

These are individual serial trials, including server startup and integrity checks.
Failures stop their current test at the first mismatch. Policies therefore execute
different numbers of calls; the JSON summary records call counts and per-policy
execution time. API and UI totals use different test counts and are not directly
comparable transport speed measurements.

Counts describe API results. A detection requires a concrete mismatch; errors and
inconclusive outcomes do not count. A surviving test only establishes compatibility
of that observed execution. The union spends three times the test budget; the
three individual policies provide equal-size comparisons.

## Uniformity and observations

There are **155 paired within-region contrasts** for `cap-long-duration`:
the selected test passes, while the upper-boundary member fails. For example,
region `reviews.standard/reviews.end` at length 1 passes with
623 minutes but fails with 720: `readTime` returns 719 minutes where
the APN expects 720. Both inputs satisfy that same region's constraints.

The upper-boundary policy detects all six seeded faults using 155 tests, whereas
the selected and interior policies detect five using the same test count. The
465-test union also detects six. This demonstrates a sensitivity to representative
choice for this constructed boundary fault; it does not establish that upper
boundaries are generally the best representatives.

A passing member and failing member of one region challenge the uniformity
assumption for this particular implementation and observation protocol. They do
not invalidate the algebraic region or the conditional testing theorem. Nor does
success on all three sampled members establish uniformity for every duration.

The richer observations matter: the earlier depth benchmark checked acknowledgments
and audit counts, which alone would not expose wrong stored durations or totals.
The present experiments do not measure a paired weak-oracle campaign, so this is
an explanation of what the added gates observe, not a measured mutation-score
improvement over that benchmark.

## Validation and reproduction

The independent finite oracle checks kinds 0–5 and durations 14, 15, 720 and 721:
24, 576 and 13,824 inputs respectively. All defined inputs are covered exactly once,
undefined boundary inputs are excluded, and all region witnesses/results pass.
This finite check does not prove all-duration or arbitrary-depth coverage.

- All 155 normally selected tests pass actual APN admission; all 310 additional
  region members pass independent membership checks and concrete APN replay.
- Fifteen Python relational/HTTP tests pass, including six new history/fault checks.
- Both controlled unmutated baselines pass, and every final database passes integrity checks.
- The restore script reconstructs the frozen suites byte for byte.
- All nine original intentions regenerate the same 64 frozen test pairs.
- Summary assertions verify full run membership, manifest/backend hashes, transport
  event agreement and the absence of error/inconclusive verdicts.

Generation timings include initialization and validation; RSS is a snapshot, not
peak memory. These richer protocols differ from the earlier depth benchmark,
so their times are not a controlled before/after comparison. Full compact evidence
is in [effectiveness-summary.json](results/effectiveness-summary.json), with
concrete representatives in [the frozen manifest](results/effectiveness-manifest.json).

From this directory, restore the published frozen stimuli and run:

```sh
node experiments/effectiveness-restore.mjs
node experiments/effectiveness-campaign.mjs --transport api
node experiments/effectiveness-campaign.mjs --transport ui
node experiments/effectiveness-campaign.mjs --transport api --variants overwrite-earlier,approval-double-count,correction-adds-old,cross-employee-correction,cap-long-duration,wrong-total
node experiments/effectiveness-campaign.mjs --transport ui --variants overwrite-earlier,approval-double-count,correction-adds-old,cross-employee-correction,cap-long-duration,wrong-total
node experiments/effectiveness-summary.mjs
```

Install Playwright Chromium or set `SATEL_CHROMIUM` to an installed executable.
Use separate ports for independently running experiments. The default campaigns
run serially and create a distinct temporary database per variant. `--db-root`
can override the live database directory. Full JSON/JSONL campaign files remain
local; the committed summary includes aggregate counts, within-region contrasts
and concrete first counterexamples. Raw event hashes allow API/UI comparison.

The manifest stores all concrete witnesses and hashes, and the restore script
requires byte-identical reconstructed suites. To perform a new selection experiment
instead, run `effectiveness-generate.mjs 1`, `2`, `3` sequentially, then
`effectiveness-freeze.mjs`; this deliberately replaces the local manifest and
requires fresh baseline/campaign evidence. Solver choices can differ across runs.

Run `node experiments/effectiveness-export.mjs` to create
`specification/hr-effectiveness.apn.json`, then import it into the editor to inspect
all three intentions. The CLI budgets used for these measurements are explicit;
GUI defaults remain unchanged. Implementation details and interpretation are in
[Increment 48](../../docs/satel/increment-48-hr-effectiveness.md).
